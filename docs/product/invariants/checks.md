# Invariant register — Checks

[Invariant register](../invariants.md) · [Spice product model](../README.md)
## Checks

| Label | Invariant |
| --- | --- |
| <a id="checks-check-settings-have-partitioned-authority"></a>**Check settings have partitioned authority** | The repository contributes packaged policy intent and lower-is-better state through the fixed tracked `spice.toml` and `baseline.toml` inputs. Packaged-arm executable names, probes, deadlines, capture, and other execution settings remain compiled; `battery/manifest.toml` owns packaged arm declaration and order, and tracked input cannot name a packaged-arm program. Tracked `policy.pre_commit` declarations own configured command labels, executable argv, and path scopes under their exact captured capability. Every setting is read from its owning source. |
| <a id="checks-configuration-fails-loudly"></a>**Configuration fails loudly** | Unknown keys are rejected at load in every layer, and an invalid bound is an error rather than a silent fall back to the default. |
| <a id="checks-a-gate-reports-and-never-files"></a>**A gate reports and never files** | A gate reports its findings in the run's typed report. No gate puts a task on the board; findings worth tracking are captured by hand with `spice task add`, on the same terms as any other work. |
| <a id="checks-a-gate-run-captures-the-exact-staged-selection"></a>**A gate run captures the exact staged selection** | Before measurement, the run captures the selected paths, staged bytes, modes, and digests as one immutable input. A later index or working-tree edit cannot change what that run judges. |
| <a id="checks-the-retained-selected-tree-is-the-sole-source-authority"></a>**The retained selected tree is the sole source authority** | One private immutable tree contains the exact staged-index or named-revision objects bound to the run's source identity. An arm consumes it directly or through a verified exact sealed mirror with separate outputs; a mirror never widens or replaces selected source, and selected bytes never come from or overwrite the caller's live source paths. |
| <a id="checks-the-fully-staged-rule-is-the-intersection-of-staged-and-unstaged-names"></a>**The fully-staged rule is the intersection of staged and unstaged names** | Staging is a captured core arm over the intersection of staged and unstaged names. A partly staged file fails that arm and prevents the combined run from publishing state. If the index moves after capture, the packaged run refuses rather than judging or publishing against mixed generations. |
| <a id="checks-the-selected-gate-battery-is-deterministic-ordered-and-immutable"></a>**The selected gate battery is deterministic, ordered, and immutable** | One run captures the explicitly selected gate arms and their order before execution. The selection cannot grow, shrink, or reorder while the run is in flight; unselected registered gates are not implicitly added. |
| <a id="checks-every-run-binds-one-actor-and-run-start-claims"></a>**Every run binds one actor and run-start claims** | Every battery requires one named active actor and captures the run-start claims into its verdict semantics. A revision-selected run may observe those claims, but rejects reconciliation before durable publication. |
| <a id="checks-returned-typed-evidence-is-collected-and-scheduler-failure-cuts-off-later-work"></a>**Returned typed evidence is collected and scheduler failure cuts off later work** | Every returned arm report retains its complete typed terminal evidence and already-started independent work is joined. A preparation, execution, panic, or observation error lowers the canonical failure cutoff: pending later arms do not start or receive synthesized rows, pending earlier work may still run, and the command returns the first canonical `ChangeGateError` with no complete report. |
| <a id="checks-an-arm-that-cannot-execute-returns-a-named-refusal"></a>**An arm that cannot execute returns a named refusal** | An arm that cannot execute returns a named refusal state with the evidence that explains it; it never impersonates a pass or admitted absence. |
| <a id="checks-not-applicable-is-explicit-admissible-evidence"></a>**Not-applicable is explicit admissible evidence** | A selected arm with no applicable input emits typed not-applicable evidence with a reason and exact declaration-owned provenance. It admits the run but is neither a measured pass, an explicit exclusion, nor a refusal. |
| <a id="checks-direct-runs-preserve-typed-terminal-evidence"></a>**Direct runs preserve typed terminal evidence** | Direct runs preserve passed, not-applicable, excluded, and named refusal states. The enclosing commit decision admits only passed and contract-owned absence or exclusion; it never erases the evidence distinctions. |
| <a id="checks-a-measured-pass-retains-the-limits-it-applied"></a>**A measured pass retains the limits it applied** | A measured pass retains the limits it applied, so it is evidence about which thresholds were in force. |
| <a id="checks-a-measure-whose-baseline-cannot-be-read-must-not-report-clean"></a>**A measure whose baseline cannot be read must not report clean** | A missing baseline and an empty baseline produce the same set and must not produce the same verdict. |
| <a id="checks-a-passing-installed-hook-prints-nothing"></a>**A passing installed hook prints nothing** | A passing installed hook emits no reply, summary, or completion line; one that finishes within a heartbeat interval emits nothing, and a longer run only names its current phase on stderr while its outcome is unknown. A direct selection command returns its complete typed report. |
| <a id="checks-configured-commands-follow-every-complete-packaged-report"></a>**Configured commands follow every complete packaged report** | Configured commands run in authored order after packaged dispatch returns a complete report, including a non-admitting Staging report. They receive captured selection paths and source digest as metadata, execute with the live repository root as their working directory, and must establish their own source binding before reading bytes when they require captured-source semantics. A preexecuted Rust typecheck, app web typecheck, or complexity policy refusal returns `change-gate-policy-regressed` before a complete report and prevents configured execution. `pre_commit_builtins = false` omits the packaged battery, not configured commands; a completed non-admitting packaged report still refuses the combined verdict and prevents selected-run state publication. |
| <a id="checks-a-step-may-be-disabled-by-configuration"></a>**A step may be disabled by configuration** | A step may be disabled by configuration, and the check system audits its own disablements, so turning a gate off is a visible act rather than an absence. |
| <a id="checks-a-scoped-rule-retunes-a-bound-over-a-declared-path-set"></a>**A scoped rule retunes a bound over a declared path set** | A scoped rule retunes a bound over a declared path set. It changes the limit and cannot disable the measure. |
| <a id="checks-policy-compiles-an-elastic-ceiling-to-one-checked-integer"></a>**Policy compiles an elastic ceiling to one checked integer** | Policy applies the finite multiplier, optional clamps, and any ratchet once to produce one checked integer ceiling. Non-finite input, an invalid range, or an unrepresentable result refuses rather than selecting a fallback. |
| <a id="checks-jitter-is-applied-over-the-headroom"></a>**Jitter is applied over the headroom** | A ceiling varies with the canonical path and its resolved provenance seed. Jitter is applied over the headroom rather than over the limit, so a jittered ceiling can never fall below base. |
| <a id="checks-jitter-seed-resolution-has-one-provenance-retaining-order"></a>**Jitter seed resolution has one provenance-retaining order** | Jitter uses the first available value in this order: published task session, published commit, active actor, candidate blob, then canonical candidate path. The report retains both the selected value and its source; the seed never becomes actor identity. |
| <a id="checks-jitter-is-deterministic"></a>**Jitter is deterministic** | The same captured path, resolved seed, and policy always produce the same integer ceiling, so replaying unchanged evidence never moves the limit. |
| <a id="checks-flex-is-headroom-not-a-new-limit"></a>**Flex is headroom, not a new limit** | An accepted value above base but at or below its elastic ceiling remains unlatched and enters time-boxed claim arbitration. A breach above the elastic ceiling proposes a latch. A latched bounded rule proposes healing at or below base; a latched `unlimited` rule proposes healing regardless of measured value because no over-base bound applies. |
| <a id="checks-inherited-debt-retains-its-exact-bound"></a>**Inherited debt retains its exact bound** | Changed inherited debt inside its elastic ceiling may pass unlatched and enter claim arbitration. Debt already beyond the committed ratchet is held to base and may fail even when the edit improves it. |
| <a id="checks-a-refusal-caused-by-a-latch"></a>**A refusal caused by a latch** | A refusal caused by a latch rather than by the value says so and names the ledger holding it. Over-the-limit and held-at-base are different diagnoses. |
| <a id="checks-latches-follow-renames-additively"></a>**Latches follow renames additively** | A renamed subject carries its latch forward without the old name being silently dropped. |
| <a id="checks-sticky-latches-and-live-claims-are-repository-shared"></a>**Sticky latches and live claims are repository-shared** | One run-start ledger is shared by every selected arm. Accepted latches and time-boxed flex claims are visible to every actor in the repository; jitter changes a ceiling, never state ownership or visibility. |
| <a id="checks-live-breaches-on-shared-subjects-are-claimed"></a>**Live breaches on shared subjects are claimed** | Live breaches on shared subjects are claimed and time-boxed. At run start an elapsed claim is treated as absent and its pruning is proposed. |
| <a id="checks-the-earliest-claimant-owns-a-contested-subject"></a>**The earliest claimant owns a contested subject** | The earliest claimant owns a contested subject, with a deterministic tie-break, so ownership never depends on scan order. A holder's accepted refresh extends its claim's expiry and keeps its original creation time, so refreshing never forfeits priority. |
| <a id="checks-a-finding-whose-subject-is-held-by-a-peer-informs-and-passes"></a>**A finding whose subject is held by a peer informs and passes** | Only a finding held by a peer redirects informationally and passes; an over-limit finding that is unclaimed or held by the current actor still blocks. The redirect names the holder and the expiry. |
| <a id="checks-accepted-reconciliation-is-scoped"></a>**Accepted reconciliation is scoped** | A partial run limits measurement and result reconciliation to observed sticky keys and preserves omitted keys that survive whole-ledger run-start rename, liveness, and expiry maintenance. An accepted exhaustive run additionally prunes live sticky keys absent from its complete observation inventory. |
| <a id="checks-gate-state-is-published-only-with-an-accepted-run"></a>**Gate state is published only with an accepted run** | Proposed latch creation, healing, rename propagation, claim pruning, and reconciliation remain transaction-local until the packaged selected run is accepted. A refused packaged selected run leaves every pressure ledger byte-for-byte unchanged, so a failed run cannot partially heal. A later configured-command refusal does not roll back state already published by an admitted packaged selected run. |
| <a id="checks-a-companion-lock-is-the-liveness-authority-for-a-private-root"></a>**A companion lock is the liveness authority for a private root** | Cleanup reclaims a private root only after acquiring its exact companion lock. A directory name or process-shaped suffix is never enough evidence that a root is abandoned. |
| <a id="checks-cleanup-removes-the-workspace-before-its-lock"></a>**Cleanup removes the workspace before its lock** | While holding the companion lock, cleanup lifts the read-only seal, removes the workspace, and unlinks the lock only after removal succeeds, retaining enough evidence for a later safe reclamation after interruption. |
